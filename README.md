# xeploy

> Interactive GitHub release pipeline CLI with multi-environment releases, meta-repo submodules, and branch sync via gh CLI.

[npm version](https://www.npmjs.com/package/xeploy)
[license](./LICENSE)
[node](https://nodejs.org)

---

## Overview

`xeploy` automates the GitHub release lifecycle through a guided interactive CLI:

- **Multi-environment releases** — select staging, uat, sandbox, and/or production in one run; RC envs share one pre-release tag, final envs share one production tag.
- **Production without RC** — create a final production release even when no `-rc.N` tag exists.
- **Release branches and PRs** — optionally create `release/X.Y.Z` branches and open PRs per environment instead of direct merges.
- **Meta-repo support** — serial releases across git submodules, then the umbrella release.
- **Old release management** — list past RC releases and promote or re-publish them.

Release notes are auto-generated by the GitHub CLI (when enabled), diffed against the previous release tag.

### Release arguments

Pass release choices as arguments to skip their prompts:

```bash
bunx xeploy --version 1.0.1-rc.6 --uat 1
bunx xeploy --uat 1                      # Prompt for the version/bump
bunx xeploy --version 1.0.1              # Prompt for the environment
bunx xeploy --version 1.0.1 --production 1
bunx xeploy --bump minor --staging 1 --uat 1
bunx xeploy --minor --uat 1 --unify       # Auto-bump and unify differing repo versions
```

| Argument | Values / behavior |
| --- | --- |
| `--version <version>` | Use `X.Y.Z` or `X.Y.Z-rc.N`, without a tag prefix. |
| `--bump <type>` | `rc`, `bugfix`, `minor`, or `major`; cannot be combined with a release version. `rc` requires staging or UAT. |
| `--rc`, `--hotfix`, `--minor`, `--major` | Bump shortcuts when `--version` is omitted. `--hotfix` uses the bugfix/patch bump. Choose only one bump option. |
| `--unify` | Automatically unify differing selected mono/meta repo versions using the highest current version and chosen bump. |
| `--staging`, `--uat`, `--sandbox`, `--production` | Each requires `1`/`0` or `true`/`false`. |
| `--version` alone | Print Xeploy's own version and exit. |
| `--help`, `-h` | Show arguments and examples. |

Both `--option value` and `--option=value` work. Release arguments start the new-release
flow directly. Omitted choices, repo selection for mono/meta projects, and the final
confirmation remain interactive.

When environment flags are provided, at least one must be enabled. These flags define
the complete set of targets: omitted environments are excluded, and the paired-environment
merge prompt is skipped. Enabled environments must have a branch configured in `.xeploy.json`.

Versions follow the same conversion as the interactive custom version: staging/UAT use
the supplied RC suffix or add `-rc.1` to a final version; sandbox/production strip the RC
suffix. Selecting both tiers creates an RC and a final release of the same base version.
Validation checks the resulting tags, including the configured prefix, for duplicates
and requires them to be greater than the latest release. Leading zeros, unsupported
suffixes, unsafe integers, unknown options, and duplicate options are rejected. Selected
meta repositories are checked before any release starts; explicit versions also cannot
downgrade selected mono package versions.

## Interactive flow

```
🚀  xeploy

? What would you like to do?
  ▶ Deploy new release
    Deploy old release
    Config

  → Deploy new release
    ? Select repos to bump  (mono/meta only; multiselect, umbrella + subprojects all checked by default)
      ▶ Umbrella (this repo)
        frontend
        backend

    ? Select release environment  (single choice; only envs with a branch in `environments`)
      ▶ staging release   (RC)
        production release (final)

    ? Select bump type  (current latest: 1.2.3-rc.4)
      ▶ Release Candidate  →  1.2.3-rc.5
        Bug Fix            →  1.2.4-rc.1
        Minor              →  1.3.0-rc.1
        Major              →  2.0.0-rc.1
        Custom

  → Config
    Edit .xeploy.json settings interactively

  → Deploy old release
    Lists all previous RC tags
    ? What to do with 1.2.1-rc.2?
      ▶ Promote to production  →  1.2.1  (final)
        Re-publish as same RC  →  1.2.1-rc.2
```

On first run, if `.xeploy.json` is missing, you are prompted to create one with auto-detected settings.

## Semver conventions

| Tag format   | Meaning                              |
| ------------ | ------------------------------------ |
| `X.Y.Z-rc.N` | Staging / UAT pre-release            |
| `X.Y.Z`      | Final release (sandbox / production) |

Release versions omit prefixes; Git tags use the configured `tag_prefix`. Go module tags additionally use the required `v` form. RC tags sort lower than final tags for the same `X.Y.Z`.

### Empty-repo behaviour

Standalone JavaScript retains its no-tag defaults: `0.1.0-rc.1` (or `1.0.0-rc.1` for a major bump). Mixed/native project planning also considers recognized file versions or configured starting versions. Release notes cover the full commit history when there is no previous applicable release tag.

## Configuration

Create `.xeploy.json` in your project root (or let the CLI create it on first run):

```json
{
  "type": "default",
  "subprojectsDir": null,
  "tag_prefix": "v",
  "generate_release_notes": true,
  "create_production_release_branch": true,
  "create_tag": true,
  "create_pr": {
    "staging": false,
    "uat": false,
    "sandbox": false,
    "production": false
  },
  "environments": {
    "develop": "develop",
    "staging": "staging",
    "uat": "uat",
    "sandbox": "sandbox",
    "production": "main"
  }
}
```

| Option                             | Type        | Default        | Description                                                                                                                |
| ---------------------------------- | ----------- | -------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ---------------------- |
| `type`                             | `"default"` | `"mono"`       | `"meta"`                                                                                                                   | auto-detected                               | Repository layout type |
| `subprojectsDir`                   | `string     | null`          | auto-detected                                                                                                              | Parent directory for mono/meta sub-projects |
| `tag_prefix`                       | `string`    | auto-detected  | Prefix for git/GitHub tags (e.g. `"v"` → `v1.0.0`); manifest versions stay unprefixed                                          |
| `generate_release_notes`           | `boolean`   | `true`         | Generate GitHub release notes vs previous tag                                                                              |
| `create_production_release_branch` | `boolean`   | `true`         | Create `release/X.Y.Z` before production merge/PR                                                                          |
| `create_tag`                       | `boolean`   | `true`         | Create git tag and GitHub release; when `false`, only bump selected native version sources                                                  |
| `create_pr`                        | `object`    | all `false`    | Open PR instead of direct merge per environment                                                                            |
| `environments`                     | `object`    | branch-matched | Maps env names to git branch names (`null` if missing); only non-null release envs appear in "Select release environments" |
| `subprojects`                      | `array`     | auto-detected  | Per-subproject config when `type` is `"mono"` or `"meta"` — see below                                                      |

Each selected project resolves its own version source. Existing JavaScript projects continue to use `package.json`; the v2 implementation also supports the formats below.

### Multi-language versions (v2)

The umbrella and each app can use different ecosystems in both mono and meta repositories. Version bumps and GitHub releases require no target-language SDK or engine. The implementation and acceptance evidence are tracked in [plan-v2.0/main.md](plan-v2.0/main.md); these changes are not a published v2 release yet.

| Ecosystem | Recognized sources |
| --- | --- |
| JavaScript | `package.json` |
| .NET | `.csproj`, `.fsproj`, `.vbproj`, shared `Directory.Build.props`; static version and application/platform properties |
| Python | Standard/Poetry `pyproject.toml`, setuptools `setup.cfg` and literal `setup.py`; Hatch/setuptools file and literal `__version__` providers; default root Git providers |
| Java | Maven `pom.xml` project/property/local-parent versions and `.mvn/maven.config` overrides; literal Gradle Groovy/Kotlin versions and `gradle.properties` |
| Rust | Package/workspace `Cargo.toml` versions; narrowly scoped local-package `Cargo.lock` updates |
| Go | `go.mod` identifies the module; `VERSION` tracks its release version |
| Flutter/Dart | `pubspec.yaml` version and numeric build suffix; normal platform builds derive their versions from pubspec |
| Unity | Game `ProjectSettings/ProjectSettings.asset`; reusable package `package.json` |
| Godot | Game `project.godot`, addon `plugin.cfg`, platform values in `export_presets.cfg` |
| Unreal Engine | Game `Config/DefaultGame.ini`, plugin `.uplugin`, recognized platform settings in `Config/DefaultEngine.ini` |
| Other / no version source | Plain-text `VERSION` |

Add optional `project` settings to the existing root configuration or any subproject. Project paths are relative to their Git repository; `version_file` is relative to that project. Existing `subprojectsDir` and `repo` settings still work. An explicit `path` supports other containers and does not have to match the displayed project name. Meta repositories use actual Git submodule paths.

```json
{
  "type": "mono",
  "subprojectsDir": null,
  "project": { "ecosystem": "generic", "version_file": "VERSION", "initial_version": "0.1.0" },
  "subprojects": [
    { "repo": "api", "path": "services/api", "enabled": true, "project": { "ecosystem": "python" } },
    { "repo": "mobile", "path": "apps/mobile", "enabled": true, "project": { "ecosystem": "flutter" } },
    { "repo": "sdk", "path": "packages/sdk", "enabled": true, "project": { "ecosystem": "go" } }
  ]
}
```

This fragment extends the existing environment/release configuration. Settings for a meta child describe that child's own repository root, without inheriting the umbrella's ecosystem.

Explicit settings override detection. Ambiguous sources prompt for a choice on an interactive terminal and save it in `.xeploy.json`; other runs fail with configuration guidance. Missing version sources use `VERSION`. Its initial version comes from an applicable tag, a configured `initial_version`, or an interactive prompt offering `0.1.0`. An explicit `--version` can supply the value for a new file directly. Discovery does not create version files. A fallback `VERSION` tracks releases; it does not automatically make a build system consume that file. Version paths must remain inside the repository and cannot traverse symlinks.

Release targets use `X.Y.Z` or `X.Y.Z-rc.N`. Python RC values are written as `X.Y.ZrcN`. Unity/MAUI display versions and Flutter platform build names that require numeric values use the base version; numeric Unreal game versions retain their revision counter; `.xeploy-state.json` retains the canonical RC identity. Commit that internal state file together with version files. A new RC or final tier advances applicable counters once; shared environments reuse the tier, and preparing the same version preserves counters. Counters remain independent between projects even with `--unify`.

Godot presets, Unity counters, .NET numeric/application properties, and Unreal plugin/Android settings have native mappings. Literal Apple plist bindings and explicit source-field overrides are also supported. Add project-specific bindings when an existing field is not automatically recognized:

```json
{
  "project": {
    "platform_fields": [
      { "file": "Build/Info.plist", "format": "plist", "key": "CFBundleVersion", "kind": "apple-counter" },
      { "file": "Build/versions.json", "format": "json", "key": "fileVersion", "kind": "numeric4" }
    ]
  }
}
```

Formats are `json`, `ini`, `yaml`, `xml`, and `plist`. INI/TOML-style bindings can supply `section`; XML `key` is the element ancestry such as `Project/PropertyGroup/FileVersion`. Kinds are `release`, `base`, `counter`, `apple-counter`, `numeric4`, `assembly`, and `suffix`; counters can specify a numeric `limit`. Bindings must identify existing literal fields. They update source metadata, not generated binaries or build-time command overrides.

Inherited/shared sources are updated once. Conflicting versions, or edits affecting an unselected shared-source consumer, stop the release. Static supported declarations are edited without executing Python, MSBuild, Gradle, Cargo, Flutter, or engines. Arbitrary computed versions, unsupported inheritance, explicit MSBuild imports, and ambiguous conditions require explicit literal source configuration. Maven `-SNAPSHOT` baselines normalize to `-rc.0`; future releases use canonical RC/final identities. CI-friendly `${revision}${changelist}` (optionally with an empty `${sha1}`) retains property bindings, including split backing files. Maven CLI overrides use one `-Dproperty=value` per line. XML version values must use explicit literal elements; expand self-closing version/suffix elements before release. Arbitrary Python version schemes and customized SCM tag rules are unsupported.

Go releases additionally create module-compatible `v` tags, including nested-module prefixes, when tag creation is enabled. A major bump requiring module/import-path changes stops before a release commit; migrate those paths manually and retry. Existing umbrella GitHub release naming remains unchanged.

Prepared edits validate all selected repositories before execution and recheck their original contents before writing. Local write batches restore affected files if a write fails; already completed remote commits/tags/releases are not rolled back automatically. Recovery uses the saved plan described below.

#### Platform mappings and computed providers

- .NET updates existing literal version, package, informational, assembly/file, and MAUI display/build fields. Local properties override shared defaults; shared declarations require selecting their consumers. Prefix/suffix versions preserve their separate fields.
- Unity games use a numeric bundle version plus Android and Standalone/Apple build counters; UPM packages keep SemVer. Unknown serialized PlayerSettings layouts stop with guidance. Editor compatibility and dependencies remain unchanged.
- Flutter separates the pubspec build suffix from release identity. Apple/Windows targets use numeric names; Android-only names may retain RC suffixes. Literal Apple plist overrides are updated; `$(FLUTTER_BUILD_NAME)` and `$(FLUTTER_BUILD_NUMBER)` remain inherited. Windows and Android bounds are validated.
- Godot updates each existing Android, iOS/macOS, or Windows export preset independently, including blank values and missing version keys in existing options sections. Windows values have four numeric components. Missing options sections require explicit setup.
- Unreal preserves engine compatibility and architecture offsets, validates effective Android store versions, and updates existing iOS `VersionInfo`. Four-part game versions retain a numeric revision; plugin `Version` advances independently of `VersionName`. Bind a source plist/build metadata field explicitly for Apple build numbers or other pipeline overrides; generated packaged output is never edited.

For Python, default root `setuptools_scm` and Hatch VCS providers use reachable canonical Git tags as release baselines, require `create_tag: true`, and keep Xeploy's release value in `VERSION`. Provider-generated files remain untouched. Nested/customized Git providers require a literal file/attribute backend; Xeploy does not emulate arbitrary provider code.

#### Historical releases and recovery

Old RC promotion reads the selected Git tree and its recorded submodule commits in disposable local checkouts. It preflights native sources before confirmation, promotes each included RC to its own final identity, and increments counters once. Release branches start from those historical commits; newer development files are excluded. Original working branches are restored on success. Re-publishing recreates GitHub releases for the existing umbrella/child RC tags without changing native files or counters.

A confirmed release saves its exact edits, targets, branch/commit expectations, and completed steps in Git's local `xeploy-release.json` metadata file. It is separate from the tracked `.xeploy-state.json`, is never staged, and is removed on success. After a Git push, tag, GitHub, or environment-sync failure, run from the original umbrella/root:

```sh
bunx xeploy --resume
```

Resume reuses the saved targets, skips completed children/steps, retries pushes, and checks existing tags/releases without moving tags or incrementing counters again. It also works with `create_tag: false`. Restore the recorded branch/HEAD and resolve unexpected local changes if recovery stops; it will not overwrite newer user work. Inspect `git rev-parse --git-path xeploy-release.json` for manual reconciliation after interruption. Remote operations are not atomic and completed releases are not automatically rolled back. A pending journal must be reconciled before starting a different release.

The public `executeReleasePlan` and `runMetaRelease` entry points use the same graph preflight as the CLI. `prepareReleaseGraph` provides the read-only native preview, and `resumeRelease` continues a saved operation. Existing package-specific helpers remain available for JavaScript callers. Freshly initialized detached meta children may switch to the configured integration branch when it points at the same commit; other detached sources require an explicit branch checkout.

### Repository types

| Type      | Detection                     | Behaviour                                  |
| --------- | ----------------------------- | ------------------------------------------ |
| `default` | one configured/detected release project | standard single-repo release |
| `mono` | multiple configured/detected projects | version-bumps selected projects, including mixed ecosystems |
| `meta`    | `.gitmodules` present         | serial submodule releases, then umbrella |

### Subproject config

When `type` is `"mono"` or `"meta"`, each subproject can be disabled from release/bump entirely with `"enabled": false` — disabled subprojects are skipped and don't show up in the "Select repos to bump" step. `"meta"` submodules (separate repos) can additionally override `create_tag`, `create_pr`, and `environments`; `"mono"` subprojects share the umbrella's `create_tag`/`create_pr`/`environments` since they release together as one repo.

```json
{
  "type": "mono",
  "subprojectsDir": "apps",
  "subprojects": [
    { "repo": "frontend", "enabled": true },
    { "repo": "internal-tool", "enabled": false }
  ]
}
```

```json
{
  "type": "meta",
  "subprojectsDir": "apps",
  "subprojects": [
    {
      "repo": "frontend",
      "enabled": true,
      "create_tag": true,
      "create_pr": {
        "staging": true,
        "uat": true,
        "sandbox": true,
        "production": true
      },
      "environments": {
        "develop": "develop",
        "staging": "staging",
        "uat": "uat",
        "sandbox": "sandbox",
        "production": "main"
      }
    }
  ]
}
```

### Version consistency (mono/meta)

When you deploy a `mono` or `meta` release and the selected repos are on **different latest versions**, xeploy shows an extra step after the bump type is chosen:

```
The latest versions of selected repos are different:
Umbrella (this repo): 1.2.3
frontend: 1.2.2
backend: 1.2.2

How would you like to bump?
- Bump each version separately (Umbrella: 1.2.4, frontend: 1.2.3, backend: 1.2.3)
- Unify them to 1.2.4
```

- **Bump each version separately** — every repo is bumped from its own current version (so repos stay on independent version lines).
- **Unify them to X.Y.Z** — all repos are set to the same version, computed from the **highest** current version among selected repos.

For `meta`, planning considers each repo's applicable Git tags and recognized native version. For `mono`, it uses each selected project's recognized version source. This step is skipped when versions already match or when a custom version was entered.

Pass `--unify` to automatically choose unification when versions conflict, for example
`bunx xeploy --minor --uat 1 --unify`. Without `--unify`, conflicts still show the choice
above. When versions already match, the flag has no effect. An explicit `--version`
already applies the same version to all selected repos.

## Programmatic API

All internals are exported for use in custom scripts:

```ts
import {
  loadConfig,
  createDefaultConfig,
  flowNewRelease,
  flowOldRelease,
  executeReleasePlan,
  getTags,
  getLatestTag,
  parseSemVer,
  formatSemVer,
  bumpVersion,
} from "xeploy";

const config = loadConfig(process.cwd()) ?? createDefaultConfig(process.cwd());
const tags = getTags();
await flowNewRelease(tags, config, process.cwd());
```
